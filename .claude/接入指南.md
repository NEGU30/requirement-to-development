# RTD 项目接入指南

> 目标：让一个新项目在 5 分钟内接入 RTD，并知道每个配置文件是干什么的。
> 大多数项目只需要跑一条命令，不需要手改 `CLAUDE.md` 或 `settings.json`。

## 1. 先跑这条命令

在 RTD 仓库根目录执行：

```bash
node scripts/install.js --target "E:/work/你的项目"
```

先预览、不写文件：

```bash
node scripts/install.js --target "E:/work/你的项目" --dry-run
```

安装器会自动：

1. 复制 8 个 skills 到 `目标项目/.claude/skills/`
2. 复制 8 个 agents 到 `目标项目/.claude/agents/`
3. 复制 5 个 hooks 到 `目标项目/.claude/hooks/`
4. 复制状态/校验 CLI 到 `目标项目/.claude/scripts/`
5. 复制机器配置到 `目标项目/.claude/reqflow/config.json`
6. **合并** `CLAUDE.md`：用 `<!-- RTD:START -->` / `<!-- RTD:END -->` 包裹，重复安装只替换这一段，不重复追加
7. **合并** `.claude/settings.json` 的 hooks：保留项目已有 hook，只替换 RTD 自己的 hook，避免重复
8. 创建 `team/{project-context,conventions,finalized-proposals}/`，只补缺失文件，不覆盖你的内容
9. 修改已有 `CLAUDE.md` / `settings.json` 前自动备份为 `*.rtd-backup-<时间>`

可选参数：

| 参数 | 作用 |
|---|---|
| `--dry-run` | 只显示将做什么，不写文件 |
| `--no-claude-md` | 不碰 `CLAUDE.md`，你自己合并 |
| `--no-settings` | 不注册 hooks，只复制文件 |
| `--no-team` | 不创建 `team/` 模板 |
| `--force-team` | 覆盖 `team/` 已有文件（默认只补缺失） |
| `--help` | 帮助 |

## 2. 接入后你只需要准备 3 样东西

| 必须 | 放哪 | 作用 |
|---|---|---|
| 项目背景 | `team/project-context/` | AI 做需求分析和推演前必读，避免方案脱离产品定位 |
| 模块清单 | `team/conventions/模块清单.md` | 流程启动时 `{模块}` 只能从这里取，禁止自创 |
| 作者标识 | 流程启动时告诉 AI | 格式「中文名-工号」，用于 `个人/{作者}/` 工作区 |

可选：

| 可选 | 放哪 | 作用 |
|---|---|---|
| UI 设计规范 | `team/conventions/UI设计规范参考.md` | 启用 `ui-spec-review`，审查 HTML 线框 |
| 协作公约 | `team/conventions/协作公约.md` | 定稿归档、人工审批规则 |
| 已有可视化 HTML | `个人/.../VisualMockups/` | 可直接接入，不需要 AI 重画 |

> 项目背景可以一个文件，也可以多个；文件名随意。AI 会读整个文件夹。

## 3. 每个配置到底管什么

### 3.1 `.claude/CLAUDE.md` — 项目宪法

**作用**：AI 进入项目后常驻遵守的硬约束。比 skill 和 hook 的约束力更强。

**内容**：

- 强制入口：新需求必须先走 `requirement-pipeline`
- 阶段顺序：0 分析 → 1 推演 → 2 可视化 → 3 PRD → 4 评审 → 5 复盘
- 评审后语义修改必须回阶段 1
- 勘误快线：仅错别字/格式，用户授权 + 日志
- 评审分级：L1 全量 / L2 回流增量 / L3 轻量
- 产物落盘路径与七类产物
- 专家派发规则

**要不要手改**：不需要。安装器用标记块合并。项目原有内容保留在标记块外。

```markdown
项目原有约束
...
<!-- RTD:START -->
RTD 内容（重复安装时整段替换）
<!-- RTD:END -->
```

想卸载 RTD：删掉标记块即可，项目原有内容不受影响。

### 3.2 `.claude/settings.json` — hooks 注册

**作用**：告诉 Claude Code 在哪些时机运行 RTD 的 5 个 hook。

| 事件 | 文件 | 作用 |
|---|---|---|
| SessionStart | `reqflow_session_init.js` | 每会话注入精简流程摘要 |
| UserPromptSubmit | `reqflow_flow_inject.js` | 有活跃流程时注入当前阶段、轮次、下一步 |
| PreToolUse (`Write|Edit`) | `reqflow_flow_guard.js` | 写可视化/PRD 前检查前置产物是否真实非空 |
| PostToolUse (`Write|Edit`) | `reqflow_post_check.js` | 写产物后自动校验字数、章节、FID、占位符 |
| PostToolUse (`Write|Edit`) | `reqflow_ui_review_remind.js` | HTML 每次修改后提醒 UI 规范审查 |

**要不要手改**：不需要。安装器合并，并保留项目已有的其他 hook。

**注意**：hook 全部是提醒模式（`exit 0`），不阻断写入。它们只帮助 AI 看见状态，最终流程纪律仍由 `CLAUDE.md` + skill + 你确认。

### 3.3 `.claude/reqflow/config.json` — 机器可读唯一源

**作用**：hooks、状态 CLI、校验 CLI 共用的路径与闸门配置。改路径时优先改这里。

| 字段 | 默认 | 作用 |
|---|---|---|
| `paths.workspace` | `个人` | 个人工作区目录名 |
| `paths.team` | `team` | 团队共享区目录名 |
| `paths.artifacts.analysis` | `RequirementAnalysis` | 阶段 0 产物目录 |
| `paths.artifacts.design` | `DesignDecisions` | 阶段 1 设计决策目录 |
| `paths.artifacts.visual` | `VisualMockups` | 阶段 2 HTML 目录 |
| `paths.artifacts.prd` | `PRD` | 阶段 3 PRD 目录 |
| `paths.artifacts.review` | `ReviewLogs` | 阶段 4 评审记录目录 |
| `paths.artifacts.logs` | `RequirementLogs` | 流程日志、`state.json`、标记 |
| `paths.artifacts.retro` | `Retrospectives` | 阶段 5 复盘目录 |
| `stages` | 0-6 | 阶段 key / 索引 / 中文名 |
| `review.fullReviewers` | 5 | L1 全量评审人数 |
| `review.lightReviewers` | 3 | L3 轻量评审人数 |
| `prd.minChars` / `maxChars` | 1500 / 5000 | PRD 字数闸门 |

**改路径时同步这 3 处**：

1. `.claude/reqflow/config.json`
2. `.claude/CLAUDE.md`
3. `team/conventions/路径与阶段约定.md`

### 3.4 `.claude/scripts/` — 状态与校验 CLI

| 文件 | 作用 |
|---|---|
| `reqflow-lib.js` | 路径解析、状态读写、文件检查 |
| `reqflow-state.js` | 流程状态：init / set / get / list / finalize / reopen |
| `reqflow-check.js` | 产物校验：PRD、需求论证、设计决策、整方案根、定稿 |

常用：

```bash
# 当前所有活跃流程
node .claude/scripts/reqflow-state.js list

# 某功能当前阶段
node .claude/scripts/reqflow-state.js get --root "个人/张三-1001/_通用/日历周视图" --field currentStage

# 校验整个方案根
node .claude/scripts/reqflow-check.js --root "个人/张三-1001/_通用/日历周视图"

# 定稿前强校验
node .claude/scripts/reqflow-check.js --root "个人/..." --final --strict
```

### 3.5 `.claude/skills/` — 8 个技能

| Skill | 何时用 |
|---|---|
| `requirement-pipeline` | 唯一入口，判断阶段、守闸门、调度子 skill |
| `requirement-analysis` | 阶段 0：要不要做、为什么做 |
| `brainstorming` | 阶段 1：2-3 个方案 + 选型，产出设计决策 |
| `visual-companion` | 阶段 2：HTML 线框 / 流程 / 页面流转 |
| `prd-generator` | 阶段 3：纯产品 PRD |
| `requirement-review` | 阶段 4：5 位专家并行评审 |
| `retrospective` | 阶段 5：增量复盘 + 总复盘 |
| `ui-spec-review` | 选配：审 HTML 的 UI 规范 |

不需要手动调用。用自然语言描述需求，`requirement-pipeline` 会调度。

### 3.6 `.claude/agents/` — 8 个专家

| Agent | 读写 | 何时派发 |
|---|---|---|
| `completeness-logic-reviewer` | 只读 | 阶段 4 完整性与逻辑 |
| `risk-reviewer` | 只读 | 阶段 4 需求真伪与风险 |
| `ux-reviewer` | 只读 | 阶段 4 用户体验 |
| `priority-reviewer` | 只读 | 阶段 4 优先级与分期 |
| `format-style-reviewer` | 只读 | 阶段 4 格式与文风 |
| `ui-spec-reviewer` | 只读 | HTML UI 规范审查 |
| `ui-designer-html` | 可写 | 阶段 2 线框制作/迭代 |
| `prd-writer` | 可写 | 阶段 3 PRD 撰写/修订 |

### 3.7 `team/` — 团队共享区

| 目录 | 放什么 | 谁维护 |
|---|---|---|
| `team/project-context/` | 产品定位、模块、架构、用户场景 | 项目负责人，AI 只读 |
| `team/conventions/` | 模块清单、协作公约、UI 规范、路径约定 | 团队 |
| `team/finalized-proposals/` | 人工审批后的定稿归档 | 审批人，流程不自动写 |

### 3.8 `个人/` — 个人工作区

```
个人/{作者}/{模块}/[功能名]/
├── RequirementAnalysis/     阶段 0 需求论证
├── DesignDecisions/         阶段 1 设计决策
├── VisualMockups/           阶段 2 HTML
├── PRD/                     阶段 3 PRD
├── ReviewLogs/              阶段 4 评审记录
├── RequirementLogs/         流程日志 + state.json + 标记
└── Retrospectives/          阶段 5 复盘
```

首次写产物时目录自动创建，不需要手工建。

### 3.9 `RequirementLogs/state.json` — 运行状态

**作用**：hooks 判断“当前在哪个阶段”的唯一机器输入。流程日志是给人看的叙述，`state.json` 是给机器看的。

关键字段：

```json
{
  "currentStage": "visual",
  "round": 1,
  "status": "active",
  "history": []
}
```

AI 每推进一个阶段就更新一次。你通常不需要手改；需要排查时用：

```bash
node .claude/scripts/reqflow-state.js get --root "个人/..." --field currentStage
```

## 4. 最小接入 vs 完整接入

| 等级 | 装什么 | 适合 |
|---|---|---|
| 最小 | skills + `CLAUDE.md` + `team/project-context/` | 只想让 AI 按流程写 PRD |
| 推荐 | 最小 + hooks + `scripts/` + `team/conventions/模块清单.md` | 日常团队使用 |
| 完整 | 推荐 + agents + UI 规范 + 复盘 | 需要评审团、可视化规范、沉淀方法论 |

安装器默认装“完整”，不想用 hooks 可加 `--no-settings`。

## 5. 安装后验证

### 5.1 文件检查

```bash
ls 目标项目/.claude/skills          # 应有 8 个目录
ls 目标项目/.claude/hooks           # 应有 5 个 reqflow_*.js
ls 目标项目/.claude/scripts         # 应有 reqflow-*.js
cat 目标项目/.claude/settings.json  # 应有 SessionStart/UserPromptSubmit/PreToolUse/PostToolUse
```

### 5.2 功能检查

打开 Claude Code 进入目标项目，说：

> 我想给待办模块加一个看板视图

预期：AI 先调用 `requirement-pipeline`，确认作者/模块/功能名/流程 A/B，然后进入阶段 0。若直接开始写方案，说明 `CLAUDE.md` 没合并成功或 hooks 没生效。

### 5.3 状态检查

```bash
node .claude/scripts/reqflow-state.js list
```

应看到刚启动的功能、轮次、当前阶段。

## 6. 日常怎么用

1. 用自然语言提需求，不需要说“调用某某 skill”。
2. 启动时回答 4 件事：作者、模块、功能名、流程 A/B。
3. 阶段 0：回答诘问，或选 A 直接自述。允许结论是“不值得做”。
4. 阶段 1：选方案，并说明为什么选它。AI 会落盘 `DesignDecisions/`。
5. 阶段 2：浏览器打开 HTML，用 📐 标注器精确指出要改哪里。
6. 阶段 3：PRD 落盘后抽查 3 处高风险内容，回 `[认可]` 或 `[改]`。
7. 阶段 4：逐条回复评审意见“处理”或“接受”。
8. 阶段 5：可随时说“帮我复盘”。

## 7. 升级 RTD

重新跑安装器即可。行为：

- skills / agents / hooks / scripts / config：覆盖为最新版
- `CLAUDE.md`：只替换 `<!-- RTD:START --> ... <!-- RTD:END -->` 段
- `settings.json`：只替换 RTD 自己的 hook，项目其他 hook 保留
- `team/`：默认只补缺失文件，不覆盖你的内容
- 修改前自动备份

```bash
node scripts/install.js --target "E:/work/你的项目"
```

## 8. 卸载 RTD

1. 删 `目标项目/.claude/skills/{8 个 RTD skill}`
2. 删 `目标项目/.claude/agents/{8 个 RTD agent}`
3. 删 `目标项目/.claude/hooks/reqflow_*`、`.claude/scripts/reqflow-*`、`.claude/reqflow/`
4. 从 `.claude/CLAUDE.md` 删除 `<!-- RTD:START --> ... <!-- RTD:END -->`
5. 从 `.claude/settings.json` 删除 command 含 `reqflow_` 的 hook
6. `team/` 和 `个人/` 的产物是你自己的数据，按需保留

## 9. 常见问题

### Q1：为什么还要合并 `CLAUDE.md`，插件不能全包吗？

`CLAUDE.md` 是**项目级宪法**，优先于 skill 和 hook。插件可以带 skill/hook，但不能替目标项目决定流程纪律。安装器已经把这一步自动化成标记块，不需要手写。

### Q2：hooks 没反应？

按顺序查：

1. Node 版本 ≥ 18：`node -v`
2. settings.json 是否合法 JSON
3. hook 命令路径是否是 `node .claude/hooks/reqflow_xxx.js`
4. 在项目根启动 Claude Code，或设置 `CLAUDE_PROJECT_DIR`
5. 手动跑：`echo '{}' | node .claude/hooks/reqflow_flow_inject.js`
6. 没有活跃流程时 inject 静默是正常的

### Q3：Windows 能用吗？

能。hooks 是 Node，不是 bash。Git Bash 只在用旧 `.sh` 包装器时需要；新配置直接用 `.js`。

### Q4：项目已有 hooks，会被覆盖吗？

不会。安装器只删除 command 含 `reqflow_` 的 hook，其他原样保留；同一 entry 里混合时会保留非 RTD hook。

### Q5：不想让 RTD 管 PRD 路径，能改吗？

改 `.claude/reqflow/config.json` 的 `paths`，同步 `CLAUDE.md` 和 `team/conventions/路径与阶段约定.md`。hooks 和 CLI 会跟随。

### Q6：评审太慢/太贵，能减少专家吗？

可以走评审分级：

- L1：5 位全量（默认）
- L2：回流第 2 轮起只审 diff + 受影响章节
- L3：仅格式/文案/单 FID，3 位，需你明确授权

AI 不能自行降档；授权理由写入评审日志。

### Q7：定稿后还能改吗？

能。说“这个功能要改版”，总控执行 `reopen`：删除 `.finalized`、轮次 +1、回到推演。不要手动改 PRD 绕过流程；仅错别字/格式可走勘误快线。

### Q8：PRD 字数 1500–5000 太死？

改 `.claude/reqflow/config.json` 的 `prd.minChars/maxChars`，自动校验会跟随。评审 skill 里的合格线也建议同步。

## 10. 一页速查

```bash
# 安装
node scripts/install.js --target "E:/work/项目"

# 预览
node scripts/install.js --target "E:/work/项目" --dry-run

# 状态
node .claude/scripts/reqflow-state.js list
node .claude/scripts/reqflow-state.js get --root "个人/..." --field currentStage

# 校验
node .claude/scripts/reqflow-check.js --prd "个人/.../PRD/01_xxx_需求文档.md"
node .claude/scripts/reqflow-check.js --root "个人/..." --final --strict

# 插件包
npm run build:plugin

# 自测
npm test
npm run sync:check
```
