# 需求推演与设计对齐 (Brainstorming Ideas Into Designs)

**本 skill 由 `requirement-pipeline` 总控在阶段 1 调度，不自行决定上下游流转。**

本 Skill 回答的是 **怎么做（HOW / WHAT）**——把已论证成立的需求转化为具体设计方案。**需求该不该做、为什么做**（WHETHER / WHY）由前置的 `requirement-analysis`（阶段 0）负责，本 Skill 不再重复质疑需求真伪，专注方案探索。

通过自然的协作对话，帮助将初步想法转化为完整的设计与规格说明。

首先了解当前项目的上下文，然后**一次只问一个问题**来完善想法。当你理解了要构建的内容后，展示设计并获取用户的批准。

<HARD-GATE>
**硬网关约束：**
在展示设计并获得用户批准之前，**绝对禁止**调用任何实现类技能、编写任何代码、搭建任何项目或采取任何实现行动。即使你认为项目"极其简单"，此规则也适用于所有项目。
</HARD-GATE>

## 反模式："这太简单了，不需要设计"

每个项目都必须经过这个流程。无论是写一个 Todo 列表、一个单功能工具类，还是修改一行配置——统统适用。往往就是这些所谓"简单"的项目，因为未经审视的假设，导致了最多的无用功。设计可以很简短（对于真正简单的项目，几句话即可），但你**必须**展示它并获得批准。

## 项目上下文加载（强制前置）

在开始推演之前，**必须先阅读** `team/project-context/` 下的项目背景文档（可单可多，全部读完），建立对本项目的产品全貌认知（定位、模块构成、架构、用户场景）。推演过程中的所有设计决策都应与此对齐。

## 代码探索（有代码时强制执行）

如果项目已有代码，**推演前必须先阅读与需求相关的现有代码**，理解当前实现方式和模块结构，避免设计方案脱离实际。

具体要求：
1. 根据需求涉及的功能模块，定位并阅读相关的**核心代码文件**（按项目实际架构分层，如界面层、业务逻辑层、数据层等）
2. 理解现有模块的**数据流、状态管理和组件结构**
3. 在推演过程中，设计方案必须**与现有代码的实现模式保持一致**，不得提出与项目已建立的模式相冲突的方案

如果项目尚无代码（全新项目），则跳过此步骤。

## 检查清单 (Checklist)

你必须为以下每一项创建一个任务（Task），并按顺序严格执行：

1. **接收阶段 0 产出** — 阅读需求论证文档 `个人/{作者}/{模块}/[功能名]/RequirementAnalysis/`，将其中厘清的**根源动机、痛点画像**（含强度维度与解决优先级）作为本次方案探索的约束基准。方案不得偏离根源动机去造无关功能；且方案的"重量"与投入时机要与痛点画像的**优先级 / 强度**相称——**P0 痛点（高频 / 高强度 / 广影响）优先做、值得重投入，低频低痛的需求用轻量解或后置**，避免杀鸡用牛刀。痛点画像的"解决优先级"应与 §2 功能分期的 P0/P1/P2 对齐（痛点 P0 → 核心功能 P0）。若阶段 0 是"强制通过"，留意其中的未解决质疑点（含反向证伪中成立的反方理由），方案设计时尽量规避相关风险。
2. **探索项目上下文** — 阅读项目概要文档；如项目已有代码，则进一步阅读与需求相关的现有代码（页面、数据流、模块结构）。
3. **提出澄清性问题** — **一次只能问一个问题**，聚焦**方案细节**（交互方式、约束条件、成功标准），不重复质疑需求真伪（那是阶段 0 的事）。**可选的提问方向包括**：用户心中是否有对标竞品或参照物？如有，请用户描述其认可与不认可的具体点（用于校准设计方向，但不记入 PRD）。若用户没有对标物，则跳过此问，不强行追问。
4. **提出 2-3 种实现方案** — 包含利弊权衡（Trade-offs）并给出你的推荐建议。**用户选定方案后，要求其给出选型理由（为什么选这个、为什么不选其他）——AI 的推荐理由不能替代用户的选择理由，两者都要记录，传递给 PRD 的设计取舍章节。**
5. **分段展示设计** — 根据复杂度分段展示，在每一部分之后获取用户的认可。
6. **用户审查设计** — 要求用户在继续之前审查最终确定的设计方案。
7. **交回总控** — 需求与方案方向对齐、用户批准，且**设计决策已落盘**后，将推演结果交回 `requirement-pipeline` 总控，由总控决定下一步流转。

## 设计决策落盘（强制 · 阶段 1 产物）

用户批准设计后、交回总控前，**必须**写入：

`个人/{作者}/{模块}/[功能名]/DesignDecisions/设计决策_[功能名].md`

这是阶段 1 的唯一落盘产物，PRD、评审、复盘都从这里追溯“为什么选 A 不选 B”。模板：

```markdown
---
文档类型: 设计决策
功能名称: [功能名]
版本: v1.0
更新日期: [YYYY-MM-DD HH:mm]
---

# 设计决策 — [功能名]

## 1. 需求锚点
- 根源动机: [来自阶段 0，一句话]
- 核心痛点: [痛点 ID / 一句话]

## 2. 候选方案
| 方案 | 核心思路 | 优点 | 代价/风险 |
|---|---|---|---|
| A | ... | ... | ... |
| B | ... | ... | ... |

## 3. 选型结论
- 选定: [方案 A]
- 用户选型理由: [用户原话/要点，不能只写 AI 推荐理由]
- AI 推荐理由: [AI 的依据]
- 为什么不选其他: [B/C 的具体排除理由]

## 4. 已砍需求
```

## 核心流程细节 (The Process)

**1. 理解想法 (Understanding the idea):**

- **必须先检查当前项目状态**（文件、架构、现有模式）。
- **评估范围**：如果请求包含多个独立的子系统，立即指出。不要在需要先拆分的项目上浪费提问时间。如果项目太大，帮助用户拆分为多个子项目，然后对第一个子项目进行头脑风暴。
- **一次只问一个问题**：如果话题需要深入探讨，拆分成多个问题逐步提问。
- **优先提供选择题**：让用户做选择比开放式问答更容易。
- **关注核心**：目的、限制、成功标准。

**2. 探索方案 (Exploring approaches):**

- 提出 2-3 种不同的方法，并说明各自的利弊权衡。
- 以对话的形式展示选项，首推你的建议方案并解释原因。
- **用户选定方案后，请其说明选型理由（为什么选这个、不选其他）。这是设计决策的核心，不能丢——AI 推荐有 AI 的理由，用户选择有用户的理由，两者都记。**

**3. 展示设计 (Presenting the design):**

- 一旦你确信理解了要构建的内容，开始展示设计。
- **按复杂度分段**：简单的部分几句话带过，复杂的部分可达 200-300 字。
- **逐段确认**：每讲完一部分，询问用户"到目前为止看起来合理吗？"
- 展示设计时必须覆盖两个层次：
  - **产品层**（为 PRD 提供原始素材）：目标用户与使用场景、核心交互方案的设计取舍（为什么选 A 而非 B）、关键假设与潜在风险。若用户提过对标竞品，将用户的竞品认知作为设计方向的参照校准点
  - **技术层**（推演时的**思考维度**，避免设计出技术不可行的方案；**不进 PRD，不要求产出技术文档**——深层技术方案留待下游开发团队）：架构可行性、数据流、明显的技术风险点

**4. 隔离与清晰的设计原则 (Design for isolation and clarity):**

- 将系统分解为具有单一职责的较小单元。
- 每个单元必须能回答：它做什么？怎么用？依赖什么？
- 保持边界清晰。

**5. 在现有代码库中工作 (Working in existing codebases):**

- 遵循现有模式。如果现有代码存在阻碍当前目标的问题（如职责纠缠），可以在设计中包含**针对性**的重构计划。
- **不要**提出与当前目标无关的重构。

## 接收评审回流 (Review Feedback Loop)

本 Skill 可接收 `requirement-review` 的评审回流。当评审团队发现问题且用户选择处理时，本 Skill 将收到：

- **待修订清单**：用户选择处理的问题项（含风险等级、问题描述、评审员建议）
- **已通过基线**：评审中已确认通过的设计项（作为保留基线，推演时不得误改）
- **评审日志路径**：完整评审上下文供参考

**回流转入时的处理方式：**

1. 先向用户确认：展示待修订清单，确认每项的处理优先级和方向
2. 针对待修订项重新进入推演流程（从步骤 2 开始，聚焦于修订项）
3. **已通过基线中的内容不得推翻重议**，除非用户明确要求
4. 推演完成后，将结果交回 `requirement-pipeline` 总控

## 设计完成后 (After the Design)

**1. 用户审查网关 (User Review Gate):**
完成分段设计并对齐思路后，要求用户进行最终确认：

> "整体设计思路已对齐。请您确认是否还有需要修改的地方？另外，如果对后续的可视化页面有什么想法（布局偏好 / 交互重点 / 风格 / 参考页面），也可以一并说说——没有也没关系，我会根据方案自动生成。确认后，我将进入可视化阶段。"
> 等待用户回复。如果有修改要求，则进行修改；**只有在用户明确批准后才能继续**。

**2. 推演选型增量复盘提议（交回总控前 · 无脑提议）：**

用户批准设计后、交回总控前，**主动提议**一次增量复盘——统一收拢本次推演的所有选型 / 砍需求决策。**不论策划本次是否纠结都提议**（策划没纠结就秒拒，成本极低）：

> "本次推演定了方案、也砍了些东西——你选 A 弃 B 的取舍、砍掉的是真不需要还是妥协，这些理由最容易事后忘，也不进 PRD。要不要花 1 分钟记个增量复盘？"

- 策划"好" → 用增量复盘简短格式即时落盘到 `个人/{作者}/{模块}/[功能名]/Retrospectives/复盘总结_[功能名].md`，追加章节 `## N. 增量复盘·推演选型 (日期)`，固定捕捉：
  - **选型与取舍**：选 [方案 A] 弃 [方案 B/C]——理由；砍掉 [某功能]——性质（真不需要 / 妥协将来要补）
  - **对标竞品认知**（如有）：认可 / 不认可点（这部分按本 skill 规则不进 PRD，**复盘是唯一归处**）
  - **审核深度**：AI 给的 2-3 方案，是逐个看再选、还是直接采纳推荐——反映本次对 AI 输出的审核质量
- 策划"不用" → 跳过，不追问

> 由本 skill 发起（它在推演现场，最清楚本次的选型 / 砍需求决策）；交回总控时告知是否已做本次增量复盘。

**3. 交回总控：**

- 用户批准设计后，本 Skill 完成，将以下信息交回 `requirement-pipeline` 总控：
  - 已确认的设计方案摘要
  - 建议的可视化维度（UI 线框图、用户操作流程、页面流转等）
  - 用户在推演过程中表达的关键偏好和约束
  - **方案选型理由**（为什么选 A、不选 B/C）——传递给 PRD 的设计取舍章节，作为用户视角的选型依据
- **本 Skill 不负责自行调用下一个 skill**，由总控统一调度。

## 核心原则总结 (Key Principles)

- **一次只问一个问题** - 绝对不要用多个问题轰炸用户。
- **首选多项选择** - 尽量降低用户的思考成本。
- **无情地遵循 YAGNI** - 从设计中剔除所有非必要功能（You Aren't Gonna Need It）。
- **永远探索替代方案** - 必须提出 2-3 个方案。
- **增量验证** - 展示设计，获得批准，再继续。
- **可视化不可跳过** - 设计批准后必须经过可视化验证，让用户"看见"而非只"读到"方案。
