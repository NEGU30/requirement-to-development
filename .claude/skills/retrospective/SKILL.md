# 需求复盘总结 Skill

## 描述

当某个功能需求经历"推演 → 可视化 → PRD 生成 → 团队评审"的完整周期后（可能包含多轮回流改版），本 Skill 负责回溯整个对话上下文，从**思考过程**而非需求变更的角度，提炼出结构化的复盘总结报告。

**核心定位**：PRD 文档记录的是**做了什么**（WHAT），评审日志记录的是**发现了什么问题**（FINDINGS），而复盘总结记录的是**为什么当初会走偏、从中能学到什么、下次如何避免**（WHY + LESSON + PRINCIPLE）。这是 本流程中唯一聚焦"策划个人成长"的环节——沉淀"烧制技艺"。

## 在流程中的位置

```
[阶段 0] 需求分析 (requirement-analysis)
    ↓
[阶段 1] 需求推演 (brainstorming)
    ↓
[阶段 2] 需求可视化 (visual-companion)
    ↓
[阶段 3] 需求文档生成 (prd-generator)
    ↓
[阶段 4] 需求评审 (requirement-review)
    ↓           ↓
用户确认      需要修改 → 回到阶段 1
    ↓
[阶段 5] 需求复盘 (retrospective)
    ↓
PRD 定稿 + 复盘归档
```

## 前置条件

本 Skill **必须在以下条件满足后才能调用**：

1. `requirement-review` 已完成团队评审，用户确认无需进一步修改
2. 需求至少经历过一轮完整的评审流程（含初始化 PRD 生成）
3. 对话上下文中存在可供分析的"关键转折点"（策划主动推翻、评审反馈、AI 质疑等）

如果需求一次性通过、没有任何修改，也应进行复盘——"为什么能一次过"本身就是有价值的正面经验。

## 触发时机

复盘分两类：**增量复盘**（流程进行中，捕捉鲜活思考）和**总复盘**（定稿后，汇总提炼）。

### 增量复盘（自动提议 · 避免上下文丢失）

关键转折点的思考过程最鲜活，但也最容易被后续对话压缩淹没。在这些点由 `requirement-pipeline` / `visual-companion` **自动提议**增量复盘，策划确认后即时落盘，追加到同一复盘文件。这样末尾总复盘读到的是"提炼过的、压缩前的"记录，而不是被压缩的原始对话。

| 触发点 | 提议方 | 提议时机 | 捕捉什么 |
|--------|--------|---------|---------|
| 阶段 0 诘问完成后 | requirement-pipeline | 阶段 0 闸门通过时 | 诘问过程、被逼出的根源动机、策划承认的假设、盲目接受/质疑的计数 |
| 推演选型 / 砍需求 | brainstorming | 推演结束、交回总控前 | 选 A 弃 B 的取舍理由、砍掉的是真不需要还是妥协、对标竞品认知（不进 PRD）、对 AI 方案的审核深度 |
| 可视化大推翻 | visual-companion | 策划推翻某版方案后 | 推翻理由、新方向与旧方向的取舍 |
| PRD 初稿审阅 | prd-generator | 策划在审核确认环节选 [改] 时 | AI 哪里写错了、怎么改的、属于哪种典型错误（捏造需求 / 漏边界 / 优先级错乱 / 物理UI描述 / 虚假设） |
| 评审回流后 | requirement-pipeline | 回流重新进入推演前 | 真人反馈原话、策划处理/接受的项及理由 |

提议格式（由各阶段执行 skill 发起，等策划确认）：

> "刚完成诘问，思考过程还很鲜活（你承认的假设、被逼出的根源动机）。要不要花 1 分钟做个增量复盘？它会追加到复盘文件，在末尾总复盘时被汇总。"

- 策划说"好" → 用增量复盘简短格式（见输出模板）即时落盘
- 策划说"不用" → 跳过，不强制、不追问

### 总复盘（定稿后 · 汇总）

- **可视化迭代后提醒**：`visual-companion` 每次生成或修改 HTML 后附带一句"如果这是最终方案，你可以说'帮我复盘'"
- **用户随时直呼**：用户说"帮我复盘"、"总结踩了哪些坑"
- **定稿时提醒**：`requirement-pipeline` 在 PRD 定稿时简短提醒

总复盘的第一步是**读取本功能复盘文件里已有的增量章节**（见检索策略），作为主力源——这些是上下文压缩前就提炼好的，比末尾回忆可靠。

## 角色设定

你是一位资深产品方法论教练。你的任务是：
- 像一个有经验的导师一样，复盘策划在需求制作过程中的思考路径
- 不仅要指出"哪里改对了"，更要深挖"为什么最初会走偏"
- 将散落在各轮对话中的教训提炼为可传承的方法论
- 对新人策划尤其有价值——帮他们把这次踩的坑变成下次的直觉

## 上下文检索策略（防 Token 超限 + 全量覆盖）

### 第零步：读取已有增量复盘（总复盘必做）

总复盘时，**先读** `个人/{作者}/{模块}/[功能名]/Retrospectives/复盘总结_[功能名].md` 中已有的增量复盘章节（`## N. 增量复盘·...`）。这些是流程进行中、上下文尚未压缩时提炼落盘的，是**最可靠的主力源**——优先于对话回忆。

若已有增量章节：以它们为主线，对话上下文只补充最近的部分。
若无增量章节（策划都跳过了）：退化为依赖对话上下文 + 产物文档，按下面的步骤走。

### 第一步：梳理事前地基

必须检索并阅读：
- `个人/{作者}/{模块}/[功能名]/DesignDecisions/设计决策_[功能名].md`——阶段 1 的候选方案、用户选型理由、砍掉的需求、关键假设
- `个人/{作者}/{模块}/[功能名]/PRD/` 下的需求文档（PRD）——最初的设计蓝图与迭代记录
- `个人/{作者}/{模块}/[功能名]/ReviewLogs/` 下的评审日志——每一轮评审发现的问题与处理结果
- `个人/{作者}/{模块}/[功能名]/RequirementLogs/` 下的流程日志与 `state.json`——完整的流程轨迹、回流次数与当前阶段

### 第二步：回溯对话中的"关键转折点"

在对话上下文中识别以下信号，这些是复盘的核心原料：

| 信号类型 | 识别关键词 / 模式 | 复盘价值 |
|----------|-------------------|----------|
| 策划主动推翻 | "不对"、"重新想了一下"、"改成"、"换个思路" | 策划自己发现了问题——说明什么地方容易产生盲区 |
| 评审反馈驱动 | "群里说"、"评审发现"、"xx 指出"、"漏了"、"缺了" | 暴露个人容易忽略的视角（如总是忽略权限、边界条件等） |
| AI 质疑 / 追问 | "你确定吗"、"有没有考虑"、"如果…怎么办" | AI 提前发现了策划没想到的分支——值得强化这种思维模式 |
| 边界条件后补 | "特殊情况"、"极端情况"、"如果用户…怎么办" | 策划的主路径思维惯性强——需要针对性提醒 |
| 平台差异后补 | "Windows 不一样"、"移动端要…"、"iOS 上…" | 策划对某端交互不熟悉——需要积累 |
| 技术约束妥协 | "做不到"、"实现成本太高"、"先砍掉"、"下个版本" | 暴露策划对技术边界的认知盲区 |
| 范围蔓延警觉 | "这个是不是也可以加"、"顺便也做一下" | 暴露需求边界控制的薄弱点 |
| **盲目接受 AI 输出** | 策划对 AI 的长输出只回"好/行/可以/确认/没问题"，无实质内容 | **暴露审核缺口——可能没细看就放行，AI 的错误会被带进下游** |
| **质疑/修改 AI 输出** | 策划对 AI 产物提出"这里改成…""为什么这样""我觉得不对"，或主动改 PRD/HTML | **正面信号——在认真审核。统计这类次数判断审核深度** |
| **策划补充独立信息** | 策划提出 AI 没提到的事实/约束/用户场景 | **正面信号——有独立思考，不是被 AI 牵着走** |

### 第三步：按序仲裁

若同一问题在多轮对话中被反复提及，以**时间线最后出现的结论**为准。

### 第四步：归纳输出

基于上述信号，按输出模板的 3 层结构（概览 / 过程复盘 / 沉淀）归纳。过程复盘用表格/列表呈现便于查看，但**有内容的填、没内容的写"本次无"，不要编案例凑数**。信号表里的根因分类、计数等不强制输出——它们只是 AI 识别转折点的参考，不是必填字段。

## 工程化与排版黄金法则

### 1. 文件存储与命名

- **存储路径（强制自动创建）**：复盘总结的保存路径为 `个人/{作者}/{模块}/[功能名]/Retrospectives/`（`{作者}` 与 `{模块}` 由 `requirement-pipeline` 启动时确认并传入）。如果在保存时该目录不存在，**必须自动创建**，禁止报错。
- **文件命名**：文件名严格遵循 `复盘总结_[功能名称].md` 的格式（如 `复盘总结_日历周视图.md`）。词与词之间强制使用下划线 `_` 连接，禁止空格。**一个功能只对应一个复盘文档**，无论经历多少次复盘、多少轮回流，都在同一文件中累积更新。
- **合并更新策略（强制）**：复盘文件已存在时，**禁止新建文件**。在原文档末尾追加新章节 `## N. 第X次复盘 (日期)`，保留历史复盘记录可追溯。首次复盘为第 1 次，后续每次复盘递增。如果同一天内多次复盘，日期精确到时分区分。

### 2. 排版边界（防幻觉）

- **分析类内容**：使用自然段落 + 要点列表
- **对比/统计类内容**：强制使用 Markdown 表格（限 5 列以内）
- **原则类内容**：使用有序列表，每一条原则**必须**附带一个来自本次项目上下文的具体案例
- **绝对禁止**：复盘内容不能写成需求文档的形式——它是反思，不是规约

### 3. 诚实原则

- 不粉饰问题。如果某次改版是因为策划的初始方案存在明显漏洞，直接指出
- 不虚构案例。每条教训必须绑定本次对话中真实发生的具体事例
- 不只讲"对"，更要讲"为什么之前错了"

## 输出模板

复盘文件有**两种格式**：增量复盘（简短，流程中追加）和总复盘（完整，首次定稿时生成）。

### 增量复盘格式（简短 · 流程进行中追加）

增量复盘只记当下的鲜活思考，不做全量提炼。追加到复盘文件末尾，章节序号接续：

```markdown
## N. 增量复盘·[事件名] ([日期])

> 本节为流程进行中的增量记录，末尾总复盘会汇总。

**当下发生的鲜活思考**：
- [只记录这次转折点的核心：发生了什么、策划怎么想、为什么这样定]
- [原话优先于转述]

**可能的教训（待总复盘验证）**：
- [一两句初步感悟，不必成熟]

**关键数据（如有）**：
- [策划质疑/接受计数、修改次数等硬数据]
```

### 总复盘格式（完整 · 首次定稿或无增量时生成）

请严格按照以下 Markdown 模板输出文档（直接输出内容，无需多余解释）：

```markdown
---
文档类型: 复盘总结
功能名称: [中文命名，与 PRD 保持一致]
复盘范围: 从需求推演到最终定稿，共 [X] 轮回流
复盘周期: [起止日期区间]
回流次数: [X] 次
存储路径: /个人/{作者}/{模块}/[功能名]/Retrospectives/复盘总结_[功能名].md
生成日期: [生成时间，精确到分钟，如 2026-05-29 14:30]
---

> **📌 阅读指引**：
> 本文档聚焦**思考过程的得失**，而非需求规则的变更（需求变更记录见 PRD 文档的更新记录章节，评审意见见 ReviewLogs）。
> 每条教训都绑定本次项目的具体案例，便于回顾时还原现场。

## 1. 复盘概览

- **功能复杂度评估**：[简单/中等/复杂]，核心原因：[一句话]
- **需求稳定度曲线**：
  - 初始方案完整度：[高/中/低]（评估最初方案与实际落地的差距）
  - 改版收敛趋势：[快速收敛 / 逐步收敛 / 反复摇摆]
- **本次最核心的教训（一句话）**：[如果只能记住一件事，应该记住什么]

## 2. 过程复盘

> 保留格式便于查看，但不强求填满——某节没内容就写"本次无"，不要编案例凑数。

### 2.1 想错与纠正

| 原始假设 | 被什么纠正 | 正确结论 |
|:---|:---|:---|

- **审核态度**：[认真逐条审 / 部分审 / 多数默认接受]
- **被 AI 救过**（AI 提前发现你没想的）：[案例，没有则写"无"]
- **被 AI 坑过**（AI 出错你没发现）：[案例，没有则写"无"]
- **决策主导**：关键决策（方案选型/优先级/取舍）[策划主导 / AI 主导 / 混合]

### 3.1 可迁移原则清单

1. **[如：先画异常分支再写主路径]**

2. **[原则名]**——来源/适用/自查

**协作类原则**（和 AI/人协作的方法论）：

1. **[如：AI 的方案至少质疑一处再接受]**
   - 来源：[本次盲目接受导致返工的案例] · 自查：[下次如何自查]
2. **[原则名]**——来源/自查

**优先内化**：[若原则超过 5 条，按"踩坑成本 × 可复用性"排序，Top 3 标注]

### 3.2 速查卡片
```

## 复盘完成后

1. **告知用户归档完成**：提示复盘总结已生成并存储至 `个人/{作者}/{模块}/[功能名]/Retrospectives/...`
2. **交回总控**：将复盘文件路径交回 `requirement-pipeline` 总控，由总控执行最终的交付核对

## 特殊规则

1. **复盘不阻塞定稿**：复盘是完全可选的，用户可以在定稿时做，也可以在定稿后任何时间回头做。不存在"不复盘就不能定稿"的强制闸门。
2. **复盘内容从对话中来**：复盘的分析素材来自本轮会话中的讨论、修改、推翻、补充。如果用户隔了几天回来做复盘，AI 需要先通读对话上下文，而非凭记忆输出。
3. **不记入 PRD 更新记录**：复盘总结是独立的元文档，不修改 PRD 内容，也不在 PRD 的更新记录中体现。
4. **复盘 ≠ 二次评审**：复盘不重新评审需求本身，只分析思考过程。如果复盘过程中发现 PRD 仍有遗漏，应退回 `requirement-pipeline` 走正常回流流程，而非在复盘中处理。
