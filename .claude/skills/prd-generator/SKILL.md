# 需求文档生成 Skill

## 描述

承接推演的设计方案与可视化确认结果，将已对齐的需求转化为一份高拓展性、结构化、且完全符合 AI 编程助手最佳读取规范的需求文档（PRD）。**PRD 同时作为正式留档产物**，生成后将结果交回 `requirement-pipeline` 总控。

**回流时直接在同一文档中修改并递增版本号**，不产生补充文档或补丁文件。

## 前置条件

本 Skill **必须在以下条件满足后才能调用**：

1. `brainstorming` 已完成需求推演，设计方案已获用户批准
2. `visual-companion` 已生成可视化方案，且用户已确认通过

如果用户跳过上述流程直接要求生成 PRD，应提醒用户先完成需求推演与可视化确认。

## 第一步：读取原始需求锚点

读取 `个人/{作者}/{模块}/[功能名]/RequirementAnalysis/需求论证_[功能名].md` 的 **§1「问题背景与反馈原文」**，将其中的「问题背景」和「用户反馈原文」作为 PRD §0 对应两块的重要参考，要防止由于上下文长度等原因，与初始需求出现偏移。首轮生成和回流迭代都要读。

> **A·资深自述标注检查**：若需求论证文档标注"A·资深自述"（流程选择 A，跳过诘问），PRD §0 的痛点详情评估性质栏须标注"策划判断（A·资深自述，未经诘问验证）"，提醒评审重点审痛点真实性。

## 使用场景

当需求推演与可视化方案均已确认，需要生成 PRD 留档并提交团队评审时调用。

## 留档定位

本 Skill 产出的 PRD 文档具有双重定位：
1. **正式留档** — 将推演和可视化的成果固化为可追溯的需求文档
2. **评审输入** — 作为后续 `requirement-review` 团队评审的审查对象

## 角色设定

你是一位具备顶级架构思维与工程化视角的 AI 产品专家。

> **派发执行**：PRD 的首版撰写与回流修订可派发 `.claude/agents/prd-writer.md` 专家代理（Task 子代理）执行——传入需求论证路径、设计方案要点与落盘路径；生成后的「审核确认」环节与用户交互仍由主对话完成。

## 工程化与排版黄金法则（必须严格遵守）

### 1. 标准化文件命名：需求文档的文件名必须严格遵循 `01_[功能名称]_需求文档.md` 的格式（如 `01_工作日历整合视图_需求文档.md`），以功能名称命名而非小应用名称，确保文件在目录中顺序明确，且在全局检索时具备极高的中文辨识度。注意：词与词之间强制使用下划线 `_` 连接，禁止使用空格。**回流修改时不创建新文件，直接在同一文件中更新内容并递增版本号。**
2. **存储路径（强制自动创建）**：需求文档的保存路径必须为 `个人/{作者}/{模块}/[功能名称]/PRD/`（`{作者}` 与 `{模块}` 由 `requirement-pipeline` 启动时确认并传入）。如果在保存时该目录不存在，**必须自动创建该目录层次**，禁止因路径不存在而报错或要求用户手动创建。
3. **严格的排版边界（防幻觉）**：
   - **业务主流程**：必须且只能使用有序列表（`1. 2. 3.`）或无序列表（`-`）描述，保证时序连贯。
   - **多维信息对比**：在描述"用户画像"、"跨端交互差异"、"优先级分期"时，**强制使用 Markdown 表格**。表格必须精简（限 6 列以内），每个单元格文字尽量不超过 50 字。**绝对禁止在表格内写复杂的交互步骤长文**。
4. **唯一功能标识（FID 机制）**：必须为每一个子功能点分配一个全局唯一的标识符，格式为 `[FID: 模块英文缩写_001]`，用于后续代码与测试用例的精准追踪。
5. **先场景后功能（强制）**：描述任何功能前，必须先回答"谁在什么情境下解决什么问题"。禁止跳过使用场景直接列出功能点。功能的优先级必须用"缺了它用户能否完成核心任务"来判定，禁止凭直觉排序。
6. **意图驱动描述（剥离物理UI）**：描述交互时，禁止使用物理方位词（如"顶部栏最右侧"、"点击右下角x号"），必须采用行为意图描述（如"触发清空操作"、"唤起更多菜单入口"），将具体视图层实现交由跨平台框架响应式处理。
7. **设计取舍必须显式记录**：如果某个功能有多种实现方案，必须在「设计理由」中说明"为什么选了 A 而非 B"。不允许呈现"唯一正确方案"的假象——这会剥夺评审时讨论替代方案的机会。
8. **产品文案用用户视角（强制）**：PRD 中出现的所有关键文案——**Toast/错误提示、空状态/未设置态、确认弹窗、引导提示、按钮文字**——必须站在**最终用户视角**写，遵循：① **清晰准确**（用用户熟悉的语言，避专业术语/行业黑话/自造词，用效果描述替代技术词）；② **友好尊重**（告诉用户"能做什么/怎么办"，不指责）；③ **简洁有效**（短句，避双重否定等绕弯句式）；④ **表述一致**（同一操作在全文功能中文案统一，如所有"网络异常"用同一句 Toast）。**入口处能说清的规则不要拖到确认弹窗里才说**（避免"先制造困惑再用弹窗补救"）。评审时由「用户体验评审员」按 `methods/user-experience.md` 的「文案审查」四原则检查。

### 9. 产品层内容深度评判标准（质量闸门）

输出 PRD 前，AI 必须对各章节自检，确保不落入"过简"或"过繁"两个极端。

#### 不合格信号（必须重新生成）

| 章节 | 过简（不合格） | 过繁（不合格） |
|:---|:---|:---|
| **需求与产品概述（§0）** | 整章缺失或省略；缺根源动机、产品定位或用户痛点（含优先级）；用户场景少于 2 个 | 罗列大段竞品分析；定位/用户角色描述过长 |
| **设计取舍（§1）** | 无方案选择理由；无砍掉的需求说明 | 过度展开技术方案细节 |
| **假设与风险（§2）** | 无假设项（写成"暂无风险"） | 每个假设附带详细的数据分析方案和埋点计划 |
| **功能设计（§3）** | 只列功能名无优先级；无设计取舍说明；无空状态/错误态覆盖 | 包含了数据表字段、API 接口名、代码类名等技术实现细节；每个按钮位置都描述 |
| **跨端差异（§4）** | 移动端和 Windows 端表现完全一样（写成"无差异"） | 列出了每个操作在各端的像素级差异 |

#### 合格线（至少满足以下所有条件）

- ✅ 需求与产品概述（§0）：含根源动机、产品定位、用户痛点（含优先级）、至少 2 个用户场景
- ✅ 设计取舍（§1）：方案选择理由 + 砍掉的需求 + 功能概览（FID 清单）
- ✅ 假设与风险（§2）：至少 1 条假设 + 1 条风险
- ✅ 功能设计（§3）：每个 FID 回答了"解决谁的问题"、标明优先级、说明交互取舍
- ✅ 全文控制在 1500–5000 字以内

#### 极限约束（防止 AI 注水）

- **禁止**在功能描述中出现字段名、类名、API 路径、数据库表名（如 `member_id`、`ScheduleEntity`）
- **禁止**将一个功能拆成 10 个以上的 FID（功能粒度过细 = 在写伪代码）
- **禁止**写成"如果不出意外一切顺利"的童话需求——至少覆盖空状态、加载失败和权限拒绝三种异常的用户侧体验

## 生成后

1. **告知用户留档完成**：提示 PRD 文档已生成并存储至 `个人/{作者}/{模块}/[功能名]/PRD/...`
2. **审核确认（交回总控前 · 强制）**：PRD 落盘后不直接交回，先要求策划做审核确认。给出 3 处高风险抽查点（AI 最易错、影响最大），让策划二选一（**无"跳过"选项——审核是 PRD 进入评审前的必经动作**）：

   > "PRD 已落盘。进入评审前，请至少抽查这 3 处：① §0 痛点详情的解决优先级 ② §1 的 P0 功能边界 ③ §2 假设的推翻条件。请选择：
   > - **[改]**：我有修改 → 告诉我改什么
   > - **[认可]**：抽查无误，继续"

   - 选 **[改]** → 按策划意见修改 PRD（在同一文档、递增版本号）；**并触发增量复盘**捕捉"AI 哪里写错了、怎么改的、属于哪种典型错误（捏造需求 / 漏边界 / 优先级错乱 / 物理UI描述 / 虚假设）"，追加到 `个人/{作者}/{模块}/[功能名]/Retrospectives/复盘总结_[功能名].md`，章节 `## N. 增量复盘·PRD 审阅 (日期)`；改完回到本审核确认环节，直至策划选 [认可]
   - 选 **[认可]** → 记录"抽查通过"，进入步骤 3

   > 由本 skill 发起（它在 PRD 生成现场，最清楚哪些点 AI 不确定）；交回总控时告知审核结论（认可 / 改过几处）。
3. **交回总控**：将 PRD 文档路径、可视化文件路径、用户关键决策、**审核结论（认可 / 改过几处）**一并交回 `requirement-pipeline` 总控，由总控决定下一步流转
