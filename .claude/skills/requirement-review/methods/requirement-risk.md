# 需求风险评审员 · 方法参考

> 查一件事：这个需求/方案**站不站得住**——痛点真不真、假设靠不靠谱、技术可不可行、会不会根本不成立。
> **呼应阶段 0 的怀疑者**（诘问时反向证伪），评审阶段再兜一道。
> 不查文档齐不齐（完整性与逻辑）、不查体验（用户体验）。

## 一、痛点真实性（§0 痛点画像复核）

痛点画像是阶段 0 诘问的产出，评审要复核"真不真"：

| 检查 | 怎么查 |
|---|---|
| 场景具体吗 | 触发场景（When/Want/But）是真实瞬间，还是抽象描述（"体验不好"这种）？ |
| 强度高估吗 | 频率/强度/影响面是不是拍脑袋？有数据/反馈佐证吗？评估性质标了吗？ |
| 优先级匹配吗 | 标 P0 的痛点，真对应高频高强广影响吗？**低频低痛配 P0 = 过度设计** |
| 绕过成本合理吗 | "用户现状怎么忍"——忍的代价可信吗，还是夸大？ |

## 二、假设与风险（§3）

**假设审查**：每个假设（§3.1）
- 有没有"推翻条件"？没写 = 假设不可验证，标问题
- 推翻条件具体吗？"用户不喜欢"是废话，"上线后 80% 用户只给自己创建"才是可验证的

**风险审查**：每个已知风险（§3.2）
- 有缓解措施吗？只列风险没缓解 = 悬着
- 缓解落地吗？"加强引导"是空话，"首次使用弹气泡指引"才落地

## 三、反向推演（核心方法 · 呼应阶段 0）

**假设"这个需求上线后效果不及预期"**，逆向推导失败原因。从三视角问：

**运营视角**：没人用 / 用几次就不用——为什么？
- 痛点其实不痛（阶段 0 误判）/ 触达不够 / 价值感知弱

**产品视角**：用了但没达成目标 / 转化低——为什么？
- 核心路径还是长 / 关键步骤有断 / 价值不直观

**技术视角**：上线后出问题 / 不可行——为什么？
- 明显技术不可行的交互 / 数据泄露越权 / 依赖不稳

**找到强反证**（让需求根本不成立的前提）且未被 §3 假设覆盖 → 作为**高风险问题**提出。

## 四、技术风险预判（PRD 阶段能看出来的）

只预判 PRD 阶段明显的技术问题（深层技术评审交开发团队技术方案）：
- 明显技术不可行的交互设计
- 用户数据（凭证、个人内容、操作记录）的明显泄露/越权风险

## 五、问题记录格式

同完整性与逻辑评审员（类型/描述/位置/风险等级/**AI确定度**/建议）。反向推演找到的"根本不成立"类问题，风险标高。

## 示例

**反向推演·产品视角**
- 问题：假设"用户愿意提前设置定时"，但若用户多临时起意、到点才想发——定时发送不匹配使用习惯
- 位置：§3 假设 H1
- 风险：高 ｜ AI确定度：有依据的推测（需访谈验证）
- 建议：H1 补推翻条件"若访谈显示 70% 用户临时起意，则功能价值存疑"
