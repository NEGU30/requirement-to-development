# 用户体验评审员 · 方法参考

> 查两件事：① **体验维度**（场景闭环/路径/空状态/信息层级/反馈/跨端）；② **旅程模拟**（走一遍用户路径查可达/状态/摩擦）。
> **旅程模拟是重点，也最容易做浅**——务必按下面的方法系统走，不要凭印象。

## 一、旅程模拟（核心方法）

### 第 1 步：建立用户路径模型

从 §0 痛点画像 + §1 场景地图，提炼 1-3 条主用户路径。每条含：
- **入口点**：用户从哪开始
- **核心步骤**：完成任务的关键步骤（通常 3-7 步）
- **结束状态**：成功 / 失败 / 放弃 / 返回
- **分支**：不同条件的分支（验证失败、数据为空等）

建议用树形缩进画出来（对话中展示，便于用户确认）：
```
用户 进会话长按消息
  ├── 选定时发送
  │     ├── [正常] 设频率+日期+时间 → 确定 → 回主表单 → 提交 ✓
  │     └── [异常] 校验失败 → 留弹窗修改
  └── ⛔ 误触关闭 → 设置全丢
```

### 第 2 步：沿路径走，做四项检查

**检查 1 · 可达性**：逐节点推进，查
- 断头路：有没有走不回去、走不下去的节点？
- 死循环：有没有困在重复操作？
- 缺失出口：每个状态有明确退出/继续吗？

**检查 2 · 状态完整性**：每个节点的所有状态都处理了吗
- 成功：有反馈吗？后续引导清晰吗？
- 失败（网络/校验/权限）：有处理吗？
- 等待（加载/处理）：有指示吗？
- 异常（意外错误）：有兜底吗？

**检查 3 · 摩擦点**：模拟完整操作，评估
- 步骤过多：核心任务超 5 步？能合并吗？
- 认知负担：要记复杂信息/频繁切换吗？
- 操作冗余：重复操作/不必要确认？
- 反馈缺失：操作后有及时反馈吗？
- 导航困惑：用户知道"我在哪、能去哪、怎么回"吗？

**检查 4 · 一致性**：对照产品/行业标准
- 术语一致：相同概念用相同术语？
- 交互模式：类似操作（删除/保存/返回）用同样模式？
- 视觉层次：重要信息突出吗？

### 摩擦点的 AI确定度（必标）

| AI确定度 | 定义 | 典型 |
|---|---|---|
| **确定有问题** | 任何用户都会困惑/阻塞，有明确依据 | 缺失出口、必填无校验、死循环 |
| **有依据的推测** | 特定条件下可能困惑，非所有用户都遇到 | 高频操作步骤略多、文案不够直观 |
| **无依据的猜测** | 基于推测，无法从 PRD 充分论证 | "用户可能觉得步骤多"无数据支撑 |

**低确定度约束**：若摩擦点里"无依据的猜测"占比 > 50%，报告开头提示"超半数为推测，建议原型/用户测试验证，而非继续审查"。

## 二、其他体验维度（旅程之外）

- **场景体验闭环**：§1 场景地图里用户要达成的目标，在 §2 功能中能找到操作路径支撑吗？
- **操作路径长度**：每个 P0 的核心路径够短吗？能合并/省略吗？
- **空状态与错误态**：首次使用/数据为空/加载失败三种状态，应对合理吗？
- **信息层级**：用户最关心的信息，视觉上最突出吗？
- **反馈机制**：操作后有即时反馈吗？等待时有进度感知吗？
- **跨端体验一致性**：同一操作 Win 和移动端的差异会让用户困惑吗？

## 三、文案审查（关键文案 · 用户视角）

> PRD 里散落在各 FID 的 Toast/空状态/确认弹窗/引导/按钮文字，按以下**四原则 + 典型问题**逐条过。核心心法：**用户视角 > 平台视角**——假设用户对产品的了解远低于预期，让最不懂的人也看得懂每条文案、放心点每个按钮。
>
> **审查范围**：从 §2 各 FID 的"核心交互流程""边界与异常""空状态"里**捞出所有出现的文案**（Toast、错误提示、空/未设置态、确认弹窗、引导提示、按钮文字），集中按下列原则过一遍。

### 3.1 四原则（钉钉产品文案标准）

| 原则 | 要求 | 审查时找的反例 |
|---|---|---|
| **清晰准确** | 用用户熟悉的语言，简单直接的短句 | 专业术语、行业黑话、自造新词（如把"流畅"写成"使用缓冲"） |
| **友好尊重** | 帮用户解决问题，告诉"能做什么/怎么办" | 指责语气（"不能分享这种格式"而非"支持 XX 格式"）、让用户挫败 |
| **简洁有效** | 短句，易扫读，必要时引导下一步 | 双重否定（"不打卡也不记录异常"）、长难句、阅读理解题 |
| **表述一致** | 同一操作/概念，名称、语法、语序全文统一 | 保存图片在不同功能里文案不一；同一错误提示两处措辞不同 |

### 3.2 典型问题清单（逐条对照）

1. **入口说清 vs 弹窗补救**：是否把本该在入口处说清的规则，拖到了确认弹窗里才解释（先制造困惑再用弹窗补救）？→ 建议入口前置告知。
2. **异常只报错不给路**：异常文案是否只说"失败了/搜不到"，没告诉"为什么 + 怎么办"？→ 补原因和下一步。
3. **角色差异没说清**：涉及多角色的操作（如呼叫方/被呼叫方），文案有没有说清"不同角色看到/听到的不同"？
4. **术语黑话**：有没有用户看不懂的专业词、行业黑话、新造词？→ 换成用户语言或用效果描述（"流畅"而非"使用缓冲"）。
5. **功能没说清**：陌生功能/创新点，有没有说清"这个按钮/能力是干嘛的、有什么值得试的"？
6. **漏掉重要信息**：不可逆/有后果的操作（删除、扣额度、定时清除），文案有没有说清后果？→ 必须告知，让用户知情决策。
7. **指责用户**：文案有没有让用户觉得"是我的错"（"不能分享这种格式"）？→ 改成告诉"能做什么"。
8. **绕弯句式**：双重否定、长定语、被动句？→ 改简单主动句。
9. **表述不统一**：同一操作（如所有"网络异常"Toast、所有"保存"按钮）全文是否一致？→ 统一。
10. **（多语言项目）术语翻译**：若涉及多语言，关键术语翻译是否准确（如"假勤"=Leave 不是 Fake）？单中文项目可跳过。

### 3.3 文案问题的 AI确定度

- **确定有问题**：明显指责用户、双重否定、同操作两处文案不一致（实证可查）
- **有依据的推测**：某术语可能让用户困惑（需假设用户背景）
- **无依据的猜测**：主观觉得"不够友好"但无具体依据——标注后建议原型/用户测试，而非死磕文案

## 四、问题记录格式

同其他评审员（类型/描述/位置/风险等级/**AI确定度**/建议）。摩擦点必标 AI确定度。

## 示例

**旅程·摩擦点**
- 问题：设"每周"频率但没选星期几，到点"确定"才报错（延迟反馈）
- 路径节点：时间弹窗 → 设频率 → [缺：选星期几] → 确定 → 校验报错
- 风险：高 ｜ AI确定度：确定有问题（校验时机就是错的）
- 建议：子规则没选全时实时标红，别等确定
