# 需求评审 (Requirement Review — Team Mode)

承接 `prd-generator` 生成的 PRD 文档，组织多 Agent 团队从不同视角并行评审，确保需求文档在正式进入开发前经过充分审视。评审结果交回 `requirement-pipeline` 总控，由总控决定定稿或回流。

## 核心定位

**本 skill 由 `requirement-pipeline` 总控在阶段 4 调度，不自行决定上下游流转。**

评审完成后将结果交回总控，由总控决定定稿或回流至推演阶段。

## 评审强度（L1 / L2 / L3）

| 档位 | 适用 | 执行方式 |
|---|---|---|
| **L1 全量**（默认） | 首轮 PRD、跨模块、P0 核心流程 | 5 位专家审完整 PRD |
| **L2 增量** | 回流第 2 轮及以后 | 5 位专家只审 `diff + 受影响章节 + 回归影响`；派发时必须附本轮 diff 范围、上一轮评审日志、已通过基线 |
| **L3 轻量** | 仅格式/文案/单 FID 局部改动 | 3 位专家（完整性与逻辑 / 需求风险 / 格式与文风）；需用户明确授权 |

- L2/L3 必须由用户确认，授权理由和档位写入评审日志。
- 即使是 L2，专家仍各自独立评审，不得互相参考。
- 不得因为“改动小”自行降为 L1 以下。

## 前置条件

1. `brainstorming` 已完成，设计方案已获用户批准
2. `visual-companion` 已生成可视化方案，且用户已确认通过
3. `prd-generator` 已生成 PRD 文档并留档

若前置条件不满足，应提醒用户先完成前置步骤。

## 触发时机

- `prd-generator` PRD 文档生成并留档后，自动流转至本 skill
- 用户明确要求对当前 PRD 进行评审
- 用户明确要求对当前需求进行评审

## 评审团队角色

| 角色 | 职责 | 关注维度 |
| :--- | :--- | :--- |
| **评审总监 (Review Director)** | 由你本人担任。组建团队、派发评审任务、汇总评审意见、产出最终评审报告。**不参与评审，仅协调** | 全局协调 |
| **完整性与逻辑评审专家**（`completeness-logic-reviewer`） | 检查需求覆盖度、边界条件、异常场景、跨端差异，以及文档前后是否矛盾、同类项是否重复 | 完整性 + 逻辑自检 |
| **需求风险评审专家**（`risk-reviewer`） | 审视需求是否站得住：痛点真实性、假设与风险、技术不可行信号，主动反向推演"什么前提下需求根本不成立"（呼应阶段 0 怀疑者，评审再兜一道） | 需求真伪 + 风险 |
| **用户体验评审专家**（`ux-reviewer`） | 审视交互路径合理性、操作复杂度、信息层级、可用性，模拟用户旅程查可达性/状态完整/摩擦点 | 体验 |
| **优先级与分期评审专家**（`priority-reviewer`） | 审查 P0/P1/P2 判定是否成立、分期切分是否合理可交付、投入是否与痛点强度相称 | 优先级 + 分期 |
| **格式与文风评审专家**（`format-style-reviewer`） | 审查结构遵从度、排版边界、FID 规范、占位符残留与 AI 味文风 | 格式 + 文风 |

> 实际评审专家为 **5 名**，均对应 `.claude/agents/` 下的真实可派发子代理；评审总监仅负责派发与汇总，不参与评审。

## 评审流程

### 第一步：接收评审输入

评审总监收集以下材料作为团队评审的输入：
- `prd-generator` 生成的 PRD 文档路径
- `brainstorming` 生成的**设计决策文档路径**（选型理由、砍掉的需求、关键假设；用于核对 PRD §1 是否忠实承接）
- `requirement-analysis` 生成的**需求论证文档路径**（供追溯根源动机与痛点画像；若为"强制通过"，其中的未解决质疑点是评审重点风险项。评审时需额外校验：**痛点是否真实成立、画像中的强度是否被明显高估**——低频低痛的需求若配了 P0 重投入，应作为问题项提出）
- `visual-companion` 生成的 HTML 可视化文件路径（作为参考）
- 用户在推演过程中表达的关键决策和约束

### 第二步：创建评审日志

在文件系统创建评审日志文件：
- **存储路径**：`个人/{作者}/{模块}/[功能名]/ReviewLogs/`（目录不存在则自动创建；`{作者}` 与 `{模块}` 由 `requirement-pipeline` 启动时确认并传入）
- **命名规范**：`[序号]_[功能模块名]_需求评审记录.md`（取目录下最大序号加 1）

评审日志初始内容：

```markdown
## 1. 评审输入
- PRD 文档: [个人/{作者}/{模块}/[功能名]/PRD/... 路径]
- 设计决策: [个人/{作者}/{模块}/[功能名]/DesignDecisions/设计决策_[功能名].md]
- 可视化文件: [HTML 文件路径列表，作为参考]
- 用户关键决策: [列出用户已确认的决策点]
- 评审档位: [L1 全量 / L2 增量 / L3 轻量（用户授权理由）]
- 本轮 diff 范围: [L2/L3 必填；L1 填“全量”]
- 已通过基线: [前几轮已确认、本轮不得推翻的设计项]

## 2. 评审团队
- ⚪ 完整性与逻辑评审 → 结论: [待填写] · 问题数: [待填写]
- ⚪ 需求风险评审 → 结论: [待填写] · 问题数: [待填写]
- ⚪ 用户体验评审 → 结论: [待填写] · 问题数: [待填写]
- ⚪ 优先级与分期评审 → 结论: [待填写] · 问题数: [待填写]
- ⚪ 格式与文风评审 → 结论: [待填写] · 问题数: [待填写]

## 3. 评审意见汇总
[待各评审员完成后填写]

## 4. 最终结论
- 评审结果: [通过 / 有条件通过 / 不通过]
- 前置修改项: [如有]
- 下游流转: [待填写]
```

### 第三步：并行派发评审专家（Task 子代理）

评审总监**同时派发五位评审专家**（完整性与逻辑、需求风险、用户体验、优先级与分期、格式与文风）。每位专家对应 `.claude/agents/` 下的一个真实子代理定义，内含各自的评审清单、方法论指引与输出格式，通过 Task 工具并行派发，在隔离上下文中独立评审。

**派发要点：**

1. **并行派发**——五条 Task 调用一次性发出，各专家互不可见、互不影响
2. **传参从简**——子代理自带评审方法与清单，主对话只需传入材料路径（PRD / 需求论证 / 可视化 HTML）与用户关键决策
3. **指定 methods 参考**（完整性与逻辑 / 需求风险 / 用户体验三位专家）——派发时提示对应 `methods/` 文档路径，子代理会先读方法再评审
4. **汇总落盘**——各专家意见交回后由评审总监（主对话）写入评审日志，不由子代理直接落盘

**派发指令模板（评审总监发给各专家子代理）：**

> "你是[角色名]评审专家。请阅读以下材料并从[评审维度]视角进行评审：
> - PRD 文档：[路径]
> - 需求论证文档：[路径]
> - 可视化文件：[HTML 路径，作为参考]
> - 用户约束：[关键决策列表]
> - **评审档位**：[L1 全量 / L2 增量 / L3 轻量]
> - **本轮范围**：[L2/L3 必给 diff 与受影响章节；L1 为全量]
> - **已通过基线**：[L2/L3 必给；不得推翻]
> - **评审方法参考**：[对应 `methods/` 文档]——**先读这个**，掌握本角色的详细评审方法与示例
>
> 请先读评审方法参考，再按以下结构输出你的评审意见：
> 1. **通过项**：你认为设计合理、无需调整的部分
> 2. **问题项**：你发现的潜在问题，每项需包含：问题描述、风险等级（高/中/低）、**AI确定度**、建议处理方式
>    - **AI确定度**（AI 对此问题有多确定，三选一）：**确定有问题**（读材料确认）/ **有依据的推测**（有部分事实但含推断）/ **无依据的猜测**（主观感觉，未实证）
> 3. **评审结论**：通过 / 有条件通过 / 不通过
>
> 评审完成后将结果交回主对话（不要自行写文件）。"

#### 完整性与逻辑评审员 — 评审清单

> 按 PRD 章节顺序检查，聚焦**文档自身质量**（齐不齐 + 矛不矛盾），不评需求真伪（那是需求风险评审员的事）。详细方法与示例见 [`methods/completeness-logic.md`](methods/completeness-logic.md)。

- [ ] **§0 需求背景**：是否含根源动机、痛点画像（含强度维度，缺一不可，全新功能也必填）？用户反馈原文是否原话不转述（无反馈则注明"来源于产品判断"）？
- [ ] **§1 产品概述**：定位、用户价值、业务价值三者是否区分清晰？用户画像是否明确？场景地图是否覆盖 ≥ 2 个情境，且每个场景的触发情境与用户目标清晰？
- [ ] **§2 功能分期与流程**：每个功能是否标注 P0/P1/P2？P0 判定是否成立（缺了无法完成核心任务）？每个 P0 的交互流程能否从触发走到完成闭环？
- [ ] **§2 异常与取舍**：每个功能是否覆盖空状态/加载失败/权限拒绝三种体验？核心功能是否说明了"为什么选 A 而非 B"？
- [ ] **§4 跨端交互差异**：同一交互在 Windows 与移动端的差异是否说明了原因？若功能仅单端，是否明确声明"仅 XX 端，无跨端差异"（而非硬凑差异）？
- [ ] **逻辑自检**：PRD 前后是否矛盾（如 §2 说支持某操作、§3 又限定不支持）？同类项是否重复或散落多处？章节间表述是否打架？发现矛盾即作为问题项提出。

#### 需求风险评审员 — 评审清单

> 审视需求"**站不站得住**"：痛点真不真、假设与风险全不全、技术可不可行、主动反向推演会不会根本不成立。呼应阶段 0 的怀疑者，评审阶段再兜一道。详细方法与示例见 [`methods/requirement-risk.md`](methods/requirement-risk.md)。

- [ ] **§0 痛点真实性与优先级**：痛点画像的场景是否具体（而非抽象）？**每个痛点**的强度（频率/强度/影响面）是否被明显高估或拍脑袋？**每个痛点的解决优先级判定是否合理**（标 P0 的是否真的对应高频高强广影响）？是否与 §2 功能分期的 P0/P1/P2 对齐？**特别警惕**：低频低痛的痛点却配了 P0 重投入的过度设计——若有，作为问题项提出。
- [ ] **§3 假设与风险**：是否有假设清单及推翻条件？已知风险是否都有缓解措施（而非只列风险）？
- [ ] **技术风险预判**（PRD 阶段能看出来的）：产品方案中是否存在明显技术不可行的交互设计？涉及的用户数据（登录凭证、个人内容、操作记录等）是否有明显的泄露或越权风险？（深层技术评审——复杂度、性能、第三方依赖、详细可行性——留待开发团队技术方案阶段，不在本阶段评）
- [ ] **反向推演**：主动找"什么前提下这个需求根本不成立 / 这个功能根本没人用"（呼应阶段 0 的反向证伪，评审再兜一次）。若找到强反证且未被 §3 假设覆盖，作为高风险问题提出。

#### 用户体验评审员 — 评审清单

> PRD 包含了场景地图，评审时应验证产品体验是否能支撑场景中用户要达成的目标。详细方法（含旅程模拟）与示例见 [`methods/user-experience.md`](methods/user-experience.md)。

- [ ] **场景体验闭环**：场景地图中用户要达成的目标，是否能在功能设计中找到对应的操作路径支撑？
- [ ] **操作路径长度**：每个 P0 功能的核心操作路径是否够短？是否有可以合并或省略的步骤？
- [ ] **空状态与错误态体验**：首次使用、数据为空、加载失败三种状态的用户感受和产品应对是否合理？是否会打击用户的首次体验信心？
- [ ] **信息层级**：产品设计要点中的信息优先级排序是否合理？用户最关心的信息是否在视觉上最突出？
- [ ] **反馈机制**：操作后是否有即时反馈（视觉/触觉/状态变化）？等待或处理中是否有明确的进度感知？
- [ ] **关键文案（用户视角）**：PRD 中出现的关键文案（Toast/错误提示、空状态、确认弹窗、引导、按钮）是否站在最终用户视角？按 [`methods/user-experience.md`](methods/user-experience.md) 的「文案审查」四原则逐条查——平台术语、指责语气、双重否定、同操作文案不统一，都是问题项。
- [ ] **跨端体验一致性**：同一操作在 Windows 和移动端的体验差异是否会让用户感到困惑？差异是否有充分理由？
- [ ] **旅程模拟**：以目标用户身份走一遍主流程（触发 → 操作 → 完成），查三件事：① **可达性**——能不能走到目标、有没有死路或断头路；② **状态完整性**——用户能感知的状态流转会不会断（如"已设置却找不到入口修改/取消"）；③ **摩擦点**——哪一步会卡住、困惑、被迫重来。发现的摩擦点按 AI确定度标注（确定有问题 / 有依据的推测 / 无依据的猜测）。

#### 优先级与分期评审专家 — 评审清单

> 以"缺了它用户能否完成核心任务"为锚审查排序与切分。完整方法见 `.claude/agents/priority-reviewer.md`。

- [ ] **P0 判定成立性**：逐个核对 P0——真正卡核心闭环的有没有被标成 P1？能完成核心任务的有没有错标 P0？
- [ ] **痛点强度 ↔ 投入相称性**：对照 §0 痛点画像（频率/强度/影响面），低频低痛却配 P0 重投入 = 过度设计，作为问题项提出
- [ ] **分期可交付**：每期是否可独立交付、独立验证？P0 是否全部落在首期？有无"第一期做完没法用"的烂尾切分？
- [ ] **依赖不倒挂**：后期功能是否被前期功能依赖？跨期共享的基础能力排期是否正确？
- [ ] **分期理由显式**：分期与取舍是否有理由记录，还是拍脑袋？
- [ ] **砍掉的需求**：✂️ 砍掉后核心任务还走不走得通？

#### 格式与文风评审专家 — 评审清单

> 只审形态与文风，不判业务内容。完整方法见 `.claude/agents/format-style-reviewer.md`，格式基准为 `prd-generator` 的输出模板与排版黄金法则。

- [ ] **结构遵从**：§0-§6 章节齐备，阅读指引与策划区/开发区分区保留
- [ ] **排版边界**：主流程用列表、多维对比用表格（≤6 列、单元格 ≤50 字）、表格内无交互长文
- [ ] **FID 一致**：全局唯一、无重号跳号，§1 概览与 §3 汇总一致
- [ ] **残留物**：模板占位符（`[xxx]`/待补充/TODO）、"详见 §X"跳转、物理方位词是否清零
- [ ] **字数区间**：全文 1500–5000 字，过简/过繁均记问题项
- [ ] **AI 味文风**：空话套话、正确的废话、童话式需求、营销腔——摘录原文并给改写建议
- [ ] **文案一致性**：同类文案全文统一，符合清晰/友好/简洁/一致四原则

### 第四步：汇总评审意见

五位评审专家完成后，评审总监：
1. 读取各 Agent 交回评审意见（子代理不落盘，由总监统一写入）
2. 对问题项去重合并，按风险等级排序
3. 写入评审日志的"评审意见汇总"章节
4. 形成最终评审结论

**评审结论判定规则：**

| 条件 | 结论 | 后续动作 |
| :--- | :--- | :--- |
| 用户确认无需修改 | **通过** | PRD 定稿，流程结束 |
| 用户确认需要修改或补全 | **需修订** | 整理修订清单，回流 `brainstorming` 走完整流程 |

### 第五步：向用户汇报并确认

评审总监向用户展示评审结果，**必须逐条确认用户的处理意愿**：

> "需求评审已完成，以下是五位评审专家的汇总意见：
>
> **通过项**（X 项）：
> - [列出各方认可的合理设计]
>
> **问题项**（X 项）：
> 1. [风险等级] [问题描述] → 建议处理方式
> 2. [风险等级] [问题描述] → 建议处理方式
> ...
>
> 评审记录已存入 `个人/{作者}/{模块}/[功能名]/ReviewLogs/...`
>
> 请逐项告诉我：对于每个问题项，您认为需要处理还是可以接受？"

用户确认后，评审总监根据用户的选择决定流转方向。

### 第六步：流转或回退

根据用户的确认结果，将评审结论和待修订清单交回 `requirement-pipeline` 总控：

**情况 A：无需修改（用户确认全部问题项均可接受，且无补充内容）**
- 评审结论记为**通过**
- 将结论交回总控，由总控执行定稿核对

**情况 B：需要修改或补全（用户选择处理部分/全部问题项，或评审讨论产生了需补充的内容）**
- 将所有需修改、补全的内容整理为**待修订清单**
- 将修订清单交回总控，由总控回流至阶段 1（`brainstorming`）重新走完整流程

**说明：本 Skill 不自行决定流转方向，所有结论和修订清单统一交回 `requirement-pipeline` 总控处理。**

**回流转入 brainstorming 时的传递内容：**
- 待修订的问题清单（含风险等级、问题描述、评审员建议）
- 本轮已通过的设计项（作为保留基线，避免推演时误改已确认的内容）
- 评审日志路径（供推演时参考完整评审上下文）

## 关键纪律

1. **评审员必须独立评审** — 各 Agent 基于相同的输入材料独立判断，不允许互相影响
2. **问题必须有建设性建议** — 发现问题的同时必须给出处理建议，不做"只提问题不提方案"的评审
3. **评审日志必须落盘** — 所有评审过程和结论必须写入文件，不允许仅停留在对话中
4. **评审总监不做业务判断** — 总监负责协调和汇总，不代替评审员做专业判断
5. **高风险问题不可降级** — 评审员标记为"高"风险的问题，总监无权自行降级为"中/低"
6. **AI确定度必须诚实标注** — 评审员不得把"猜测"标成"确定"。"风险高 + AI确定度低"（严重但 AI 未实证）的问题，总监应向用户标注"此问题需查证后再决定是否处理"，而非当成确定问题直接推进
