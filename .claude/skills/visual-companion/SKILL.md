# 需求可视化伴侣 (Visual Companion Guide)

**本 skill 由 `requirement-pipeline` 总控在阶段 2 调度，不自行决定上下游流转。**

基于 HTML/浏览器的可视化验证伴侣。承接推演的设计产出，将文字方案转化为可交互的视觉草图，在用户直观确认后将结果交回总控。

## 核心定位

**本 skill 是 `brainstorming` 与后续开发流程之间的强制门禁，不是按需调用的辅助工具。**

设计推演完成后，用户通过"看"比通过"读"更容易发现问题、验证逻辑、做出决策。因此，无论需求看起来多简单，都必须经过可视化确认。

> **派发执行**：HTML 线框原型的首版制作与迭代修改可派发 `.claude/agents/ui-designer-html.md` 专家代理（Task 子代理）执行——传入设计方案要点、落盘路径（方式一同时给 `html-generation-spec.md` 路径）；与用户的确认、标注、复盘交互仍由主对话完成。

## 可视化范围（产品向）

需求阶段可视化的受众是**策划 + 评审**（产品人员），聚焦验证**产品设计**——用户能看到、能体验到的。**技术向的图（数据流向、架构关系）移交 `generate-tech-proposal`（技术方案阶段）**，不在本阶段。

本 skill 根据设计方案复杂度，覆盖以下维度中的**全部或部分**（至少覆盖一项）：

### 维度 1：业务流程图（业务怎么走通）

- 业务从头到尾怎么走通（开始→关键业务节点→结束），**和系统/功能无关，只看业务本身**
- 多角色参与时用泳道图（角色间的业务交接，如"用户→系统→管理员"）
- **业务闭环检查**：确认业务能走通、没有走不通的环节
- 用内联 SVG 绘制（流程图 / 泳道图）

**业务流程图 vs 功能流程图（维度 3）**：

| | 业务流程图（本维度） | 功能流程图（维度 3） |
|---|---|---|
| 回答 | 这件事从头到尾怎么走通 | 用户在系统里每步怎么操作 |
| 粒度 | 业务环节（粗） | 操作步骤（细，点按钮/进页面） |
| 例子 | 用户想发言→匿名发言→群友看到→管理员处理 | 点匿名开关→输入消息→点发送 |

> 先画业务流程（确认业务闭环），再画功能流程（设计具体操作）。业务流程图是功能流程图的前置——业务走不通，功能再细也没用。

> 复杂度匹配：简单需求（单一角色、线性流程）可以跳过业务流程图，直接画功能流程。

### 维度 2：UI 线框图（尽量动态可交互）
- 页面布局、导航结构、组件排列
- 不同屏幕尺寸的适配效果
- 视觉层级与信息密度
- 用 **HTML+CSS（div + flex/grid）** 绘制——UI 线框本质是页面结构，用真实 DOM 比 SVG 更合适，且响应式自适应
- **尽量做成动态可交互**：静态线框验证不了"点按钮跳哪、弹窗怎么出、列表怎么筛"。能用交互演示的，就别只画死图。可视化阶段验证的就是交互流，不是像素

**离线单文件下实现交互的手段（都内联，不破坏离线）**：

- **优先用纯 CSS 交互**（无需 JS，最稳）：
  - Tab 切换：`<input type="radio">` + `:checked` + `~` 选择器
  - 折叠/展开：checkbox hack（`:checked` 控制显隐）
  - 弹窗/抽屉：`:target` 锚点 或 `:checked`
  - 悬浮态：`:hover`（按钮高亮、菜单预览）
  - 模拟选中：`:checked` / `:focus`
- **需要逻辑时用内联 JS**（直接写在 `<script>` 里；外部 CDN 一律禁止，见「离线自包含」规范）：
  - 点击按钮切换状态/页面
  - 列表筛选、搜索
  - 表单输入与即时校验
  - 简单动画（class 切换 + CSS transition）
- **不用框架库**：原生 JS 足够可视化原型，不引入 Vue/React/jQuery（JS 库 CDN 已在「离线自包含」规范禁止）

**交互演示原则**：
- 关键操作路径（主 CTA、跳转、弹窗）必须能点——让用户在浏览器里真实走一遍，比看静态图更能发现问题
- 不必追求完整业务逻辑，演示"点了之后界面怎么变"即可（mock 数据、假跳转都行）
- 每个可交互元素加 `cursor: pointer` + 悬浮反馈，让用户知道"这个能点"

### 维度 3：用户操作流程图
- 用户完成核心任务的步骤路径（主流程 + 异常分支）
- 多角色协作的**用户侧**操作（如审批流：发起方提交 → 审批方处理 → 发起方收结果）
- **用户视角的状态流转**（如"日程：未设置 → 已设置 → 已提醒 → 已完成"，是用户能感知的状态，非内部字段流转）
- 用内联 SVG 绘制（流程图 / 状态图）

**流程图绘制纪律**：

1. **多角色用泳道图**——涉及多角色协作时，竖向分列（每列一个角色），节点放对应角色列，跨角色交接用横线、同角色用竖线，角色用不同颜色区分
2. **先粗后细**——先画主流程（开始→关键节点→结束），确保主干走通；再补支线和异常
3. **异常4问**——对流程每一步问 4 个问题，补全异常场景：
   - ① 这步一定能操作吗？有没有前置条件？（权限/登录/数据为空）
   - ② 这步一定能到下一步吗？（要不要填完才能继续）
   - ③ 这步会不会失败？（网络异常/超时/冲突）
   - ④ 用户误操作怎么办？（误点/误删/误提交）
4. **最后过一遍**——画完后顺着每条路径走一遍，检查有没有遗漏的分支或走不通的路径

> 技术状态机（字段级状态、内部流转、时序图）移交技术方案阶段，不在本维度。

### 维度 4：页面流转图
- 页面间的跳转关系（用户从哪进、能跳到哪、怎么返回）
- 导航结构层级（主导航 / Tab / 抽屉的从属关系）
- **返回路径**（返程入口是否清晰——如"回到今天"按钮、返回上一级、取消操作后的落点）
- 用内联 SVG 绘制（页面节点 + 跳转箭头，返回路径用虚线区分）

> 页面流转图聚焦"用户在应用里的导航地图"，和维度 3 的"用户操作流程"互补：操作流程图讲"完成一件事的步骤"，流转图讲"页面间的结构关系"。

**保真度与复杂度相匹配：** 简单需求可能只需一张线框图，复杂需求可能四个维度都需要。根据 brainstorming 产出的设计方案判断，不要为可视化而可视化。

**移交技术方案阶段（generate-tech-proposal）的图（不在本阶段做）**：
- ❌ 数据流向图（数据链路 / 模块间数据传递 / 接口调用时序）
- ❌ 架构关系图（模块划分 / 依赖方向 / 职责边界 / 组件复用）

## 存储路径与命名规范

- **存储目录**：`个人/{作者}/{模块}/[功能名]/VisualMockups/`（如目录不存在，在保存前自动创建；`{作者}` 与 `{模块}` 由 `requirement-pipeline` 启动时确认并传入）
- **文件命名规范**：`[序号]_[功能模块中文名]_可视化方案.html`（**文件名不带版本号后缀，固定单文件**）
  - 序号：与同方案根下 `PRD/` 对应需求文档的序号保持一致（通常为 `01`），确保可视化文件与 PRD 一一对应
  - 功能模块中文名：与 PRD 文件中的功能名称保持一致
  - 示例：`01_工作日历整合视图_可视化方案.html`
  - **沿用历史文件名**：若目录下已存在历史可视化文件（含旧规则下带 `_v1` 后缀的），迭代时直接沿用该文件名原地修改，**不重命名**，避免破坏既有引用与归档索引
- **单文件优先**：尽量将所有可视化维度合并到一个 HTML 文件中，**多维度时用 tab 页签组织**（每个维度一个 tab、默认显示第一个；单维度直接单页不用 tab）。只有在内容量确实过大时才拆分多个文件
- **多文件时保持统一前缀**：若必须拆分（按维度），所有文件共享相同的前缀 `01_[功能模块中文名]_`，仅用后缀区分维度
  - 示例：`01_工作日历整合视图_可视化方案_UI.html`、`01_工作日历整合视图_可视化方案_流程.html`
- **版本演进：单文件原地更新 + 文件内修订记录**（与 PRD 策略一致，**不再生成 `_v2`/`_v3` 多文件**）
  - 用户反馈修改时，**用 Edit 工具在当前 HTML 文件上原地改**——不另存新文件、不覆盖出新副本。这样既快，也不让废弃版本在文件夹堆积
  - 版本演进信息通过文件内的「修订记录」区块保留（见下方文件模板），**不靠多文件堆历史**：修订记录只记「版本 / 日期 / 改动摘要」的语义
  - 视觉层面的"新旧对照"由 git 承担：`git show 旧commit:xxx.html` 可直接打开任一历史版本对照，`git diff` 看两版差异——这是"有 git 时多文件版本管理属重复造轮子"的同一结论
  - 版本号规则（写在修订记录的"版本"列）：初版 `v1.0`；每次小修改（文案/样式/局部元素）`v1.1`、`v1.2`…；大方向推翻（换布局/换交互模式）进位 `v2.0`——与 PRD 版本号规则一致
  - **例外**：仅当用户明确要求「这一版单独留作对比」时，才把当前文件复制一份另存为 `..._对比_v2.0.html`；这是用户主动行为，不是默认流程

## 工作流程 (Workflow)

### 第一步：接收设计方案

从 `brainstorming` 接收以下信息：
- 已确认的设计方案摘要
- 需要可视化的维度
- 用户在推演过程中表达的关键偏好和约束
- **可视化偏好**（如有：pipeline 在阶段 1 闸门后询问的页面布局 / 交互重点 / 风格偏好 / 参考页面；用户没说则无，按推演方案自动生成）

### 第二步：生成或接入 HTML 可视化文件

先与用户确认输入源：**AI 生成** 还是 **用户提供外部 HTML**。

#### 方式一：AI 生成（默认）

根据设计方案，判断需要覆盖哪些可视化维度，生成**完整的、独立的 HTML 文件**。

- **初版用 Write 生成完整文件；后续迭代一律用 Edit 在该文件上原地改**（版本演进策略见「存储路径与命名规范」段，动作见第四步）。生成首版时记得填写文件内「修订记录」的 `v1.0` 首行
- **单文件优先**：尽量将所有可视化维度（业务流程、UI 线框、用户操作流程、页面流转）合并到一个 HTML 文件中。**多维度时用 tab 页签组织**（每个维度一个 tab，结构见 `html-generation-spec.md` 的文件结构模板）；单维度直接单页，不用 tab
- 只有在内容量确实过大（单文件超过 1000 行）时才拆分，且拆分后所有文件必须共享 `01_[功能模块中文名]_` 前缀
- 每个维度区域顶部写明：**这个可视化要验证什么问题？用户应该关注什么？**
- **生成后必须执行离线自检**（判定标准见 `html-generation-spec.md` 的「离线自包含」小节）：扫 HTML 源码确认无外部引用，发现即改为内联，改完才算可交付

#### 方式二：用户提供外部 HTML

用户已有现成 HTML（设计师稿、其他工具生成、现成原型），直接接入，不重新生成。

1. 用户指定外部 HTML 文件路径
2. **复制**到方案根 `VisualMockups/` 下，命名为 `01_[功能名]_可视化方案.html`（与 AI 生成的落盘规则一致）
3. 在文件内「修订记录」区标注 `v1.0 · 外部提供`（来源 + 日期）
4. **不修改外部 HTML 的内容**（用户提供的文件，不擅自改）

**兼容性提示**（告知用户，不强制处理）：
- 外部 HTML 可能不是离线自包含（用了 CDN / 外部资源）—— 在离线环境可能显示不全
- 外部 HTML 没有内嵌标注器（FAB）—— 如需标注元素，用书签版 `partial-annotation-bookmarklet.html`（推荐 Chrome）

> **两种方式的后续步骤完全相同**：第三步（通知用户查看）→ 第四步（反馈迭代）→ 闸门检查。用户确认、PRD、评审都不关心 HTML 来源。

### 第三步：通知用户查看

在终端中告诉用户已生成的 HTML 文件的绝对路径，并提示用户在浏览器中打开。

> 话术示例："我已根据设计方案生成了可视化方案，请用浏览器打开查看（推荐 Chrome，标注体验最佳）：
> - `个人/{作者}/{模块}/[功能名]/VisualMockups/01_工作日历整合视图_可视化方案.html` ，看后请在对话中告诉我是否认可，或提出修改意见。
> 如需精确指定改哪个元素，用页面自带的「selector 标注器」（生成的 HTML 已内嵌，无需安装）：打开 HTML → 右下角点 📐 浮动按钮 → 开启标注 → 点元素写改动 → 导出清单 → 贴给我。"

### 第四步：收集反馈与迭代

- 用户确认通过 → 记录确认结果，本 Skill 完成，可进入后续开发流程
- 用户提出修改 → **用 Edit 工具在当前 HTML 文件上原地改**，并在文件内「修订记录」追加一行（版本号递增 + 改动摘要），重复第三步
- 用户对某个维度有疑问 → 针对性补充该维度的可视化，不强制全部重做

**两种修改反馈方式**：

| 方式 | 说明 | 适合 |
|---|---|---|
| 文字描述 | 用户口头说"把XX改成YY" | 简单修改、整体方向调整 |
| **selector 清单**（推荐） | 用户用页面自带的「selector 标注器」标注（HTML 已内嵌），导出 `selector \| 元素签名 \| 改动` 清单贴给 AI | 精确指定改哪个元素、改什么 |

**按 selector 清单修改的规则**：

收到格式 `序号. selector | <元素签名> | 改动描述` 时：
1. 按 selector 在 HTML 里定位元素（如 `.cal-event:nth-child(2)`）
2. 核对元素签名（标签+class+文本）确认定位准确
3. 按改动描述修改（颜色/文字/尺寸等属性级改动）
4. 多条改动**从后往前应用**（避免前面的结构改导致后面 nth-child 偏移）
5. **用 Edit 在当前 HTML 文件上原地改**（按改动描述做属性级/结构级替换），并在文件内「修订记录」追加一行——同第四步迭代规则

> **selector 标注器默认内嵌在生成的 HTML 里**（见下方「内嵌标注器」小节），用户打开 HTML 即可在右下角看到 📐 浮动按钮，零安装、Edge/Chrome/Firefox 全通用。仅当要标注**非 本流程生成的任意网页**时，才用书签版（见 `partial-annotation-bookmarklet.html`；浏览器选择与 Edge 兼容方案见「内嵌标注器」小节）。

**修改后附带提醒（区分定稿复盘与增量复盘）**：

每次原地修改 HTML 后，在结果末尾附带一句提醒。按修改性质区分：

- **小修改（文案/样式微调）**：仅提醒定稿复盘入口
  > "如果这是最终方案，你可以说'帮我复盘'，我会回溯整个修改历程。"

- **大推翻（用户推翻了之前的方案方向，如换布局/换交互模式）**：额外提议增量复盘——推翻理由此时最鲜活，末尾总复盘时可能已被压缩
  > "这一版推翻了之前的方向。推翻理由现在最鲜活，要不要花 1 分钟做个增量复盘记下来？避免末尾回忆不准。说'好'就开始，说'不用'继续。"

增量复盘由 `retrospective` skill 执行，追加到复盘文件。用户拒绝则跳过，不追问。

### 第五步：生成归档索引并交回总控

全部可视化方案通过后：

1. **留存确认**：确认所有最终版 HTML 文件已保存在 `个人/{作者}/{模块}/[功能名]/VisualMockups/` 下
2. **告知用户**：可视化产物已留档，文件路径为 `个人/{作者}/{模块}/[功能名]/VisualMockups/.../01_xxx_可视化方案.html`
3. **交回总控**：将以下信息交回 `requirement-pipeline` 总控：

调用时需传递以下信息：
- 已确认的设计方案摘要
- 各可视化文件路径及对应维度
- 用户在推演和可视化过程中表达的关键决策和约束

完成后将可视化结果交回 `requirement-pipeline` 总控，由总控决定下一步流转。

## HTML 生成规范（详见独立文件）

> **用户提供外部 HTML 时不额外读取** `visual-companion/html-generation-spec.md`（HTML 已有，不需要生成规范）。

## 设计建议 (Design Tips)

> 以下是正文规范之外的补充建议（保真度匹配、验证目标、UI 可交互等核心规范见上方各维度与工作流，不在此重复）。

- **用颜色区分层次** — 主流程用深色，异常分支用浅色，未确定的部分用虚线
- **标注决策点** — 在流程图中标明需要用户做出选择的关键节点
