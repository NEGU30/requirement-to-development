# UI 规范审查 (UI Spec Review — 选配工具)

## 核心定位

**本 skill 是选配工具，不嵌入 主流程（阶段 0-5）。**

visual-companion 生成 HTML 后，用户**可选调用**本 skill，对 HTML 的 UI 设计做规范符合度检查。规范文档独立、可换——不同项目放不同规范，skill 不用改。

> **派发执行**：审查执行可派发 `.claude/agents/ui-spec-reviewer.md` 专家代理（Task 子代理，隔离上下文、只读），传入 HTML 路径与规范文档路径即可；报告结构与流程不变。

## 触发时机

- visual 生成 HTML 后，用户明确要求"审一下 UI 规范"/"检查 HTML 的 UI 设计"
- **不自动触发**（非 主流程环节，不是阶段 0-5 的一部分）

## 输入

1. **HTML 文件**：visual-companion 生成的可视化 HTML（UI 线框）
2. **UI 设计规范文档**：当前项目的设计规范（**可换**）
   - 默认路径：`team/conventions/UI设计规范参考.md`
   - 或用户指定路径

## 审查流程

### 第一步：读取输入

- 读 HTML 文件（visual 产出）
- 读 UI 设计规范文档（默认 `team/conventions/UI设计规范参考.md`，或用户指定）
- 若规范文档不存在 → 提示用户："未找到 UI 设计规范文档。请提供路径，或先放规范到 `team/conventions/UI设计规范参考.md`。规范格式：按维度组织（类型分级 + 场景映射 + 决策流程 + 禁止 + 反馈）。"

### 第二步：按规范检查 HTML UI

逐维度检查 HTML 的 UI 设计合理性（对照规范文档的类型分级 + 场景映射 + 决策流程）：

1. **按钮**：类型选择（主要/次要/描边/错误/文字）是否匹配操作语义？组合规范（双按钮/三按钮）？尺寸场景？同行同尺寸？
2. **颜色**：语义使用（主题色/错误色/文字色/背景色/边框色）是否合理？是否用了非规范色？是否硬编码色值？
3. **圆角**：分级（S/M/L/XL）是否匹配元素高度？是否硬编码圆角值？
4. **弹窗**：类型（确认/带输入/单选/多选/多操作）是否匹配场景？结构（标题/内容/底部）规范？尺寸合理？
5. **蒙版**：分级（S/M/L）是否匹配阻断程度（轻微/部分/完全）？是否硬编码透明度？是否非黑色蒙版？
6. **投影**：分级（S/M/L）是否匹配组件层级（导航/卡片/弹窗）？是否为非浮层元素加投影？

> 每维度：读规范文档该维度的「类型分级 + 场景映射 + 决策流程 + 禁止」，判断 HTML 的 UI 设计是否合理。规范文档没有的维度跳过。

### 第三步：产出审查报告

按以下结构输出（纯文本返回用户，不自动改 HTML）：

1. **通过项**：UI 设计合理、符合规范的部分（要点列表）
2. **问题项**：每项含
   - 【维度】（按钮/颜色/圆角/弹窗/蒙版/投影）
   - 【问题描述】（HTML 里哪里不合理）
   - 【规范依据】（规范文档怎么说）
   - 【建议处理方式】（怎么改）
3. **审查结论**：通过 / 有条件通过 / 不通过

报告交回用户，由用户决定是否修改 HTML（**不自动改**）。

## 规范可换（关键设计）

- skill 本身（SKILL.md）只定义**审查流程**（怎么审），**不含规范内容**
- 规范是**独立文档**（`team/conventions/UI设计规范参考.md`），项目特定
- **换项目换规范**：替换 `team/conventions/UI设计规范参考.md`，skill 不用改
- 规范文档格式：按维度组织（类型分级 + 场景映射 + 决策流程 + 禁止 + 反馈）

### 安装时放规范

将你项目的设计规范文档放到目标项目的 `team/conventions/UI设计规范参考.md`。

## 边界

- **不嵌入 主流程**（阶段 0-5 不变，不影响 requirement-pipeline 调度）
- **不自动触发**（用户可选调用，像选配工具）
- **不自动改 HTML**（产出报告，用户决定改不改）
- **规范可换**（不同项目不同规范，skill 不用改）
- **只审 HTML UI**（不审 PRD、不审业务逻辑、不审代码）
- **规范文档没有的维度跳过**（如规范只定义了按钮/颜色，则只审这两维）
